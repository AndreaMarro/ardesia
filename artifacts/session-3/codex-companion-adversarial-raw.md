No-ship. The exact freeze matches, but the live path can display unattested electrical values, split provider/audit commits from board state, silently lose audit records, and misrepresent diagnostic restoration.

Findings:
- [high] Provider failures can still become locally fabricated UI readings (apps/studio/src/toolhost/ToolCanvasEmbeddable.tsx:1336-1342)
  The accepted response carries solveOutcome and diagnostics, but onAccepted retains only the scene and operationId. If topology is accepted while solving returns ok:false with empty currents/voltages, the UI still updates localScene and later displays values recomputed by computeElabMnaView or batteryLedCurrentMa. Users can therefore see numerical readings that contradict the provider's blocker result.
  Recommendation: Persist solveOutcome and diagnostics with the accepted receipt and suppress numerical readings whenever the provider did not attest them. If local recomputation remains, label it explicitly as non-attested and retract provider-derived claims.
- [high] Provider commit and success audit happen before the board compare-and-swap (apps/studio/src/roomSimulationComposition.ts:180-220)
  simulation.applyOperation commits runtime state and produces its success audit before the board is re-read. A concurrent layout/provenance change makes line 208 reject the write-back; board.write can also fail afterward. The caller then receives failure and the board has no wire, while the durable audit already records a successful operation. This falsifies end-to-end atomicity and leaves retries with misleading history.
  Recommendation: Stage the provider result, perform an atomic board CAS, and only then finalize runtime state and the success audit. Otherwise implement tested compensation and record a distinct partial-commit outcome.
- [high] Audit persistence failures are deliberately discarded (apps/studio/src/toolhost/caps/board.ts:182-186)
  Promise.allSettled drains audit writes but ignores every rejection and returns success solely from the board response. A quota, permission, or storage failure after board.write therefore produces a successful mutation with no audit record and no counter, event, or diagnostic. ToolHost's audit catch and non-rejecting idle chain reinforce the same blind spot.
  Recommendation: Keep fail-soft behavior only if audit rejection becomes observable through a structured diagnostic, metric, or event. Inspect settled results and add an oracle where every audit append rejects after a successful board write.
- [high] The injected runtime is allowed to grade its own topology integrity (apps/studio/src/toolhost/caps/simulation.ts:206-228)
  solve checks topology invariance by comparing digests, but both digests are generated by the same injected _api.sceneDigest that the comments treat as potentially malicious. A runtime whose digest function returns a constant can add or remove a wire during solve, pass the equality check, and have the modified state committed with a receipt claiming the old digest.
  Recommendation: Compute and compare a host-owned canonical scene projection or host-owned digest before and after solve/serialization. Treat the provider digest as untrusted metadata rather than the integrity oracle.
- [high] The live cold-restore path drops diagnostics and runtime state (apps/studio/src/roomSimulationComposition.ts:155-164)
  The live composition creates a new ToolHost without simulationInitialState. Its write-back persists only the rich scene, not the serialized runtime envelope containing lastSolverResult, diagnostics, and applied operations. After a short-circuit operation and reload, topology can reopen but the prior diagnostic evidence cannot; tests that inject simulationInitialState exercise a different harness than this live path.
  Recommendation: Persist a versioned, room/instance/digest-bound runtime envelope and pass it as simulationInitialState during live restoration. Otherwise retract the diagnostic cold-restore claims from product and architecture documents.
- [high] One unresolved storage or RPC promise can wedge every simulation embed (apps/studio/src/roomSimulationComposition.ts:327-339)
  The queue is scoped to the entire store, and its current turn is released only when the caller's finally executes. The caller holds that turn across kill-switch storage, MessageChannel calls, and audit.idle; tool-to-host SDK calls have no timeout. If any dependency never settles, every later mutation in every room sharing the store waits forever behind the unresolved turn.
  Recommendation: Apply bounded deadlines and cancellation to kill-switch lookup, handshake, RPCs, audit drain, and write-back; always close ports after timeout. Add a causal test with a never-resolving audit/store operation proving subsequent mutations recover.
