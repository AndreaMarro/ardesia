# ADR-0005 — Calendar as an explicit projection of four Core sessions

Status: implemented for local MockCalendar/ICS; Google remains NOT_CONFIGURED.

Canonical dates are `study_editions.sessions` explicit ISO timestamps with offsets and the edition's IANA timezone. Calendar derives UTC instants without rewriting this JSON, enrollment, payments or learning/attendance facts. There is no public edition/date/roster administration endpoint in this slice. Four ordinal meeting identities derive from edition+slot, independently of dates. Source hashes include the complete ordered sessions JSON, timezone and edition state. Reordering/replacement therefore invalidates previews and requires a new explicit teacher confirmation; the adapter never sorts or silently edits canonical sessions.

The Core verifies a persisted principal and SQL ownership/membership before decoding edition or intent content. Preview/confirm/reconcile are owning-teacher operations; a confirmed member may download a published ICS intent for that edition. Preview freezes UTC sessions, timezone, ordinal identities, public course title, target scope, timestamp, sequence, source version and expiry. Confirmation requires the exact hash/version, explicit boolean true and an actor-scoped idempotency key. New body fields cannot supply dates, actor, role, account or arbitrary provider URL. A direct Google target fails501.

Five small adapter tables hold targets/checkpoints/channels, intents, durable four-event mappings, minimized external cache and notification deduplication. The canonical pedagogical journal is not their state database. A single active publishing intent per target prevents overlapping replacements. Preparation commits stable provider IDs before I/O; acknowledgements update mappings separately, and completion records an immutable Core receipt. A lost acknowledgement can be retried with the same intent/key without creating another event. There is no atomic transaction spanning DB and provider. A partially published intent that becomes stale requires operator review; there is no automatic abandonment or lease-based replacement in this bounded version.

The Core depends on a small CalendarPort, not the concrete mock. The mock is an in-process, thread-safe test double with full bounded snapshots. External scope derives from provider/account/calendar, shared across editions; mapping/session IDs also include edition identity. Checkpoints/cache are scoped to the authorized edition-target association. It models idempotent event IDs, etag conflicts, lost acknowledgements, external edits and410. Its external event store resets on app restart; durable Core mappings do not. Reconciliation reports missing/changed/cancelled external events for teacher review, without editing Core. It stores only IDs, instants, status and etag from the external snapshot, never private titles. A cursor-version comparison rejects a late snapshot rather than replacing a newer committed cache.

Mock notifications are in-process test inputs, not public webhooks. Channel/token/resource/expiry are validated; delivery identity is deduplicated without assuming consecutive or ordered message numbers. Each fresh notification reconciles actual provider state. Missed notifications require an explicit reconciliation call; channel renewal is a manual mock helper, with no scheduler or live-watch claim.410 clears only the affected cache/checkpoint and fetches a full snapshot; mappings and all canonical facts remain, including if that full fetch fails. Google pagination/OAuth/watch renewal/HTTPS receiver are not implemented.

ICS consists of four independent VEVENTs, stable ordinal UIDs, frozen UTC DTSTAMP, SEQUENCE, UTC DTSTART/DTEND, CRLF, escaped text and UTF-8 folding at75 octets. No RRULE, ATTENDEE, invitation or private imported title is emitted. Unapproved canonical edition dates are TENTATIVE. Repeated download of the same current intent yields the same bytes; the file hash differs from the preview hash. ICS creation/import is not native-client live sync, and native hosts are untested.

SQLite schema3 marks the adapter tables as required. Recognized schema2 databases/backups may bootstrap only the additive Calendar state (and the already-supported old catalog metadata during verified restore); canonical table loss remains an error. Schema3 Calendar table loss is rejected by constructor, health and restore. The version marker is written after Calendar DDL. Migration10 defines PostgreSQL constraints/indexes/default-deny RLS, with no browser grants; only owning tutors mutate adapter state, while published ICS metadata is readable by actual members through the backend. Applying/running that migration is an explicit operator action.
